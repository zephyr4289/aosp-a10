01 · Pipeline river

One run = one campaign. Six-hour jobs, 35-day chain.

Plan computes the contract and mhash. Sync banks immutable src-<mhash> once. Turbo prewarms partitions in parallel while slot-1 drives the system graph. Slots relay exact ninja state. Postcheck reads INDEX.json — never guesses. Conveyor re-dispatches on slice, verifies on done, goes RED on capacity/error.

plan → sync → turbo×3 ∥ slot-1..6 → postcheck → verify | conveyor | RED → publish (zip + SHA256SUMS + flash-guarded.sh + SAFETY_REPORT + boot/dtbo/vbmeta)
plan & validate→sync src-<mhash>→turbo boot/vendor/product∥slot-1..6 exact-resume→postcheck INDEX→phase→verify 14-pt/conveyor slice/RED fail

Relay math (why no linear redo)

ccache-only: T = W + ΣP(k) — soong 15–25m + Java/Kotlin + dex re-run every slice.
out/ relay: T = W + k·O(1) — restore 3–8m + unpack 5–10m + bank 10–15m. Flat in k.

Zero-staging chunker

tar out/ → zstd -T0 -3 → split -b 1900M --filter 'gh release upload'. Zero local parts. SHA256SUMS per part. 2 GiB asset ceiling respected.

02 · Compressed steel volume

75 GiB logical on 65 GiB physical — the deadlock that killed #30/#34–36.

Source (~35G) + warm out/ (~40G) never fit /mnt. Storage v2 mounts everything on a hard-capped sparse btrfs loop (compress=zstd:1,noatime). Text compresses 2.2–3×, objects 1.4–1.8×. 15–25 GiB stay free. fstrim returns holes. Any provisioning failure degrades to plain layout — never aborts. Pre-bank cleanup can never delete source in volume mode.

Why turbo can't brick

Stubs are acceleration only: system slice authoritative (--ignore-existing), final m relinks stale edges, gate runs on final images. Turbo failure costs time, never safety.

Conveyor

done→verify · sliced→slice (re-dispatch) · capacity/error/exhausted→RED. done requires a real zip. Needs FORGE_DISPATCH_TOKEN for instant chain, else weekly cron resumes — never silent, never looping.
